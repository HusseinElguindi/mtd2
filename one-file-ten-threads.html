Ten Threads

Re-opening a 2020 Stack Overflow question — why is multi-threaded file I/O in Rust slower than Go? — and answering it with measurements instead of intuition. The seek was never the problem.

Question datedMay 2020

The original bug had five causes, and the suspected one was last

The program downloaded a file in ten HTTP range requests, each thread writing its range into one shared output file. The asker's own hypothesis was that Go won because syscall.Pwrite is one syscall while Rust needed seek + write. That's a real difference. It's also the smallest thing on this list.

Dominant

The mutex serialized the downloads, not just the writes. Arc<Mutex<File>> held across seek-and-write means ten threads take turns at the one thing they were parallelized to avoid. This is why "open the file separately in each thread with no locking" was mysteriously the fastest attempt — it deleted the contention.

Dominant

The program was network-bound the whole time. At 100 MB/s, pulling 64 KiB off the wire takes ~640 µs. The syscall under suspicion costs ~2.3 µs. Tuning it optimizes 0.4% of the work.

Real bug

BufWriter and BufReader were doing nothing. Both were sized equal to the I/O size. A write at or above capacity bypasses the buffer and goes straight to the kernel — so the wrapper was pure overhead with none of the benefit. Confirmed under strace.

Real bug

write was used where write_all was needed. Write::write may write fewer bytes than you handed it and return that count; ignoring it silently corrupts the output. Go's File.WriteAt loops internally and errors on a short write — so the Go version didn't have this bug, and a correctness gap was quietly masquerading as a performance gap.

Negligible

The extra lseek. Measured below. It costs 98 ns and adds 3–6% to a 64 KiB write — a rounding error against everything above it.

Verdict

Collapsing two syscalls into one saves 3–6% of the write, which is roughly 0.015% of the time to pull that data over a 100 MB/s link. The hypothesis was correct in mechanism and wrong in magnitude.

And the buffer was a no-op

Ten 64 KiB write_all calls through a BufWriter, counted with strace -f -e trace=write -c:

A buffer only buffers when it is larger than the writes you push through it. Sized at exactly the I/O size, it is a memcpy you pay for and never amortize.

The fix is positional I/O, and it shipped in 2017

FileExt::write_all_at takes &self, not &mut self, and does not touch the file cursor. That means an Arc<File> is safely shareable across every thread with no mutex and no per-thread handle — each thread writes to its own byte range, concurrently, and nobody contends on anything.

// One shared handle. No Mutex. No cursor. No BufWriter.
use std::os::unix::fs::FileExt;
const CHUNK: usize = 256 * 1024;

let file = Arc::new(File::create(&out)?);
file.set_len(len)?;                // preallocate; avoids i_size locking
let part = len.div_ceil(threads);

std::thread::scope(|s| {           // per range:
    let resp = ureq::get(url)
        .header("Range", &format!("bytes={start}-{end}"))
        .call()?;
    let mut body = resp.into_body().into_reader();
    let mut buf = vec![0u8; CHUNK];
    let mut off = start;
    loop {
        let n = body.read(&mut buf)?;
        if n == 0 { break; }
        file.write_all_at(&buf[..n], off)?;   // ONE pwrite, no lock
        off += n as u64;
    }
});

Verified end to end: 50 MB pulled over ten threads against a local range-serving HTTP server, output SHA-256 matching the source.

Three traps worth knowing

  • Windows is not symmetric. std::os::windows::fs::FileExt::seek_write does move the cursor. It is not a drop-in pwrite for concurrent use on a shared handle — cross-platform code needs the positioned-io crate or separate handles.
  • O_APPEND silently defeats pwrite. The kernel ignores the offset and appends anyway. If your file-opening helper takes an append: bool, make sure a range downloader isn't passing true.
  • Preallocate with set_len. Ten threads all extending the file fight over i_size; sizing it up front removes that.

What actually changed since 2020

Not the answer. write_at predates the question by three years, and the correct pattern would have worked verbatim in May 2020. What changed is everything around it — the wrong version got substantially less wrong, and the ergonomics got much better.

1.15.0 · 2017FileExt::write_atThe fix was already available, three years before the question.
1.33.0 · 2019write_all_atShort-write-safe positional write. The version you actually want.

1.67 · 2023std::sync::mpsc → crossbeamThe std channel was replaced wholesale with the crossbeam implementation.

Is Rust worth it over Go for this shape of work?

For a range downloader specifically: the two are equivalent, and Go is easier to get right on the first try. File.WriteAt loops on short writes for you, goroutines are cheaper than threads, and the runtime's scheduler handles fan-out without you thinking about it. That is exactly what the 2020 result reflected — not a language performance gap, but Go's API steering the asker into the correct pattern by default while Rust's Seek + Write path let them build a lock around it.

Rust's edge shows up past the point where I/O stops being the bottleneck: when you're transforming bytes in flight, when allocation pressure and GC pauses start showing in tail latency, when you want the compiler to prove the sharing is sound rather than testing for it, or when you need the deep-queue asynchronous I/O below. Below that line, pick on ecosystem and team familiarity, not throughput.

Networking ecosystems: Rust is ahead on HTTP/3, Go is ahead on everything being boring

Rust

  • hyper 1.11.0 and reqwest 0.13.4 — both extremely widely deployed.
  • rustls sits among the 60 most-downloaded crates; memory-safe TLS is the default rather than the adventurous option.
  • quinn is mature QUIC, with quinn-udp shipping inside Firefox. HTTP/3 in reqwest still needs RUSTFLAGS="--cfg reqwest_unstable".
  • Cost: async Rust is a real learning curve, and runtime choice is a commitment.

Go

  • net/http in the standard library covers most of what people import a crate for in Rust.
  • QUIC is the gap: golang.org/x/net/quic still says "not ready for production usage", and HTTP/3 in net/http is open with milestone Unplanned.
  • Third-party quic-go is the practical answer and is genuinely good.
  • Cost: less room to tune, and no equivalent of the deep-queue I/O story below.

Go also has no io_uring in its runtime — golang/go#31908 has been open since May 2019 — and the netpoller doesn't cover regular files, so a blocking file write pins an OS thread.

io_uring: 6× the work per CPU-second, or 2× slower

The benefit is not a property of io_uring. It is entirely determined by whether the operation genuinely blocks and how many you have in flight. Both outcomes are reproducible on the same box within minutes of each other.

Wins

One thread at queue depth 128 does roughly 2× the throughput of 64 blocking threads at a third of the CPU per operation — about 6× the work per CPU-second — without 64 stacks and 64 scheduler entities. The CPU efficiency is as much the point as the throughput.

Loses

io_uring was 2× slower. Buffered file I/O usually can't complete inline in the ring, so the kernel punts it to io-wq worker threads — you pay a thread handoff to make asynchronous an operation that was never going to block. This is the result most "io_uring is faster" writeups omit.

The costs are real

  • Buffer ownership fights Rust. The kernel holds your buffer until completion, so you cannot hand it a &[u8] and drop the future — the kernel would still be writing into freed memory. That's why tokio-uring uses owned-buffer APIs that give the buffer back with the result. Cancellation is the sharp edge.
  • Ecosystem split. compio, tokio-uring, and glommio all take that part of your program off mainline tokio.
  • It gets disabled. Google turned it off across ChromeOS, Android, and production after a run of exploits; /proc/sys/kernel/io_uring_disabled exists for exactly this, and many managed container platforms block it. You need a fallback path.
  • Linux only, with behavior that genuinely varies by kernel version.

What we'd carry forward

Reach for positional I/O before reaching for a lock. If threads write to disjoint ranges, write_all_at on a shared Arc<File> needs no synchronization at all. A mutex around a file is usually a sign the wrong API was picked.

Find the bottleneck's order of magnitude before optimizing anything. A 2.3 µs syscall inside a 640 µs network read is not the problem, and no amount of correct reasoning about syscall counts changes that.

A buffer sized to your I/O size is not a buffer. Writes at or above capacity bypass it. Verify with strace -c rather than assuming.

Prefer write_all/read_exact over write/read. Short writes are rare enough to pass every test and real enough to corrupt production output.

io_uring pays when the operation blocks and many are in flight — O_DIRECT storage, high-connection-count servers, anything above roughly 50–100k ops/sec. It costs you when ops complete in page cache, when there are only a handful of large sequential ones, or when you're bandwidth-bound. For the downloader, its benefit is zero: ~150 write syscalls per second at 2.25 µs is 0.03% of runtime.

Publish the box with the numbers. Everything here ran on a 2 vCPU container over a virtio-backed disk, not real NVMe. The absolute IOPS are far below what a real device does; the ratios are the part that transfers, and on faster hardware the io_uring gap typically widens, since syscall overhead stays fixed while the device gets quicker.
